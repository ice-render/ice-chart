# 列存（虚拟）系列：把百万级数据从「对象数组」里拿出来

> 状态：**已实现**（`series.virtual: true`，目前覆盖散点图，2026-09-21）。
> 本文记录机制、对外契约、实测账，以及**可复用边界** —— 以后要把它推广到折线 / 热力图 /
> 实时流 / 引擎虚拟源，先读这一篇，不要重新调研。
>
> 相关的施工记录与验收数据在 `plans/scatter-large-data-virtualization.md`，
> 仓库内的改动纪律在 `AGENTS.md` 的「虚拟（列存）系列」一节。

## 1. 问题：不是"画得慢"，是"表示得贵"

100 万散点在默认视图下**全部可见**（1M 个点挤进 960px）。最初的判断是"绘制太慢"，
于是做了可见窗口裁剪与密度抽稀（每像素列约 2 点）—— 平移从 472.7ms/帧降到 8.4ms。
但内存账没动，拆开看是这样：

| 账单 | 100 万点的占用（量级估算，总账见 §4 的实测） |
|---|---|
| 原始数据项（`[x, y]` 元组，每点一个数组） | 40 ~ 70 MB |
| 归一化产出的 `DataPoint`（每点一个对象） | ~50 MB |
| 运行期按点缓存（`pixels` 2n + `effective` 2n + `itemProgress` n） | 40 MB |

**真正的大头是"每点一个对象的表示税"**，渲染只是把这份账单付到台面上。
所以这次动的不是绘制代码，是数据的**表示形态**：数据以列（`Float64Array`）为准，
`DataPoint` 退化成"要看某个点时临时合成的视图"。

## 2. 机制：六条可迁移的原则

只有第 1 条与"散点"绑定，其余五条是通用的 —— 这才是本文值得沉淀的部分。

1. **值与表示解耦**：列是事实来源，数据点对象是按需合成的视图，不再常驻。
2. **读点收敛到统一入口**：数量走 `pointCount`，取点走 `pointAt(i)`，
   逐点热循环走标量访问器（`xValueAt / yValueAt / baseAt / topAt / sizeAt`）。
   入口统一之后，**换存储形态是局部改动，不是全仓重写** —— 这是这次最大的一笔架构红利。
3. **热的与冷的分开**：逐点绘制/插值的循环只取标量（不合成对象）；
   提示框、无障碍镜像、事件参数这些"每次只有一两个点"的冷路径才合成对象。
4. **全量缓存 → 按需重算 + 二分定位**：`pixels`（2n）这类"以空间换查询"的默认策略，
   在点数超过阈值后换成"以计算换空间"，并用二分/索引把计算压到 O(log n)。
5. **数据域 / 单调性 / 尺寸范围与建列同一趟算完**：后续任何环节都不再扫全量数据。
   每多扫一遍 100 万点就是几毫秒，而且中间产物会立刻被丢弃。
6. **不支持的用法显式报错**：宁可抛错，也不要"静默少画 / 空提示框 / 悄悄降级"。
   语义边界写进类型文档（见 `src/types.ts` 的 `virtual`）。

## 3. 对外接口

```js
// 推荐：直接给列（Float64Array 会被直接采用，不再复制一份）
series: [{ type: 'scatter', virtual: true, data: { x: Float64Array, y: Float64Array } }]

// 也收：元组数组（适合几十万级、应用侧本来就是数组的场景）
series: [{ type: 'scatter', virtual: true, data: [[0, 1], [1, 3], ...] }]

// 也收：纯数值数组（x 取下标）
series: [{ type: 'scatter', virtual: true, data: [1, 3, 5, ...] }]
```

内部契约（改数据点存储 / 命中路径前必读，与 `AGENTS.md` 同步）：

- **读点只有三个入口**：`pointCount` / `pointAt(i)`（断点仍是 `y: null`）/ 标量访问器。
  虚拟系列的 `points` 是**空数组**，直读 `points[i]` 会静默少画。
- **归一化后释放原始 `data`**：建完列就把 `option.series[i]` 换成不含 data 的副本
  （百万级元组本身就要 40~70MB）。列存缓存在图表实例上，供同一轮的第二遍归一化复用。
- **不物化按点缓存**：虚拟系列不建 `pixels` / `effective` / `itemProgress`；
  渲染与命中都从「列 + 同一份比例尺」现算 —— **同一个公式、同一份数据**，
  不存在"两套坐标"的分叉。这是 `AGENTS.md` 铁律 2（像素缓存唯一）的唯一例外。

## 4. 实测

同一把尺子、同一台机器、真机 Chromium、100 万点（普通路给元组，虚拟路给列）：

| 口径 | 普通（元组 + DataPoint） | 虚拟（列存） |
|---|---|---|
| 堆（CDP 取堆，GC 后） | 125.2 MB | **2.2 MB** |
| `points.length` / `pointCount` | 1,000,000 / 1,000,000 | **0** / 1,000,000 |
| `pixels.length` | 2,000,000 | **0** |
| 命中 p50 / p95 | 0.8 ms / 1.1 ms | **0.00 ms / 0.00 ms** |
| 平移 p50 / p95（60 帧拖拽） | 16.7 ms / 17.5 ms | 16.7 ms / 17.4 ms（都在 60fps 上限） |
| 构建 | 752 ms | 640 ms |

示例页：`examples/large-data-scatter-virtual.html`（页面右上角实时显示点数、数据点对象数、
像素缓存长度与堆占用）。

## 5. 复用边界：哪些场景值得用

**判定规则**：`每点的"表示税" × 点数` 是否已经超过你愿意为交互延迟付出的重算成本。
经验阈值：**>10 万点**、或**每点内存 >50 字节**、或**必须与视口解耦**（不管放大到哪都要能拖）。

| 场景 | 为什么契合 | 还差什么 |
|---|---|---|
| 折线 / 面积（监控、长历史、科学曲线） | 与散点同一套 (x, y)，收益相同；LTTB 抽稀可与列存叠加 | 把虚拟分支提到通用基类 |
| K 线 / 看盘类 | tick 级数据、缩放平移最频繁、多 pane 联动回显，"回到最新 N 根"天然是百万级窗口操作 | 一行多条列（OHLCV）+ 历史分页加载 |
| 热力图 | 本质是 rows×cols 的稠密矩阵（1000×1000 就是 100 万格），现在是每格一个数据点 | 直方图/聚合桶先算好再存列 |
| 实时流（数据 append） | 现在是每 tick 全量重建；列存 + **环形缓冲**才能做真增量（丢最老、加最新，只重算新点） | 环形缓冲与"窗口平移"语义 |
| 亿级数据 | 列存 + **分块 + 可见窗口惰性加载** | 分块读取器与缓存淘汰 |
| 列式数据源对接 | 与列式格式（Apache Arrow / Parquet 这类）的内存布局同构，可以像今天"直接采用 Float64Array"一样直接采用 | 输入适配层（成本很低） |
| Worker / GPU 路线 | `Float64Array` 可 zero-copy 转移给 Worker；同一条列也能直接上传成 GPU 顶点缓冲 —— 对象数组做不到 | 主线程只画、Worker 算的管线 |
| 引擎虚拟源 | 引擎侧已有同思路的原型（50 万 × 3 系列、typed 15.3MB、120fps、命中 <0.1ms）；打通后图表的列可以**直接喂给引擎**，省掉中间拷贝 | 两层接口对齐 |
| 无障碍镜像 / 节点列表 | 现在每系列最多建 200 个节点，就是因为 100 万节点会爆；列存 + 窗口化后可以只给视口内的点建节点 | 视口变化时增量增删 |

**什么时候别用**（列存救不了，或者反而更贵）：

- 数据量小（几万以内）：多一层间接，冷读还要合成对象，收益为负 —— 所以默认关闭、显式开启。
- 每个点带独立语义小结构（桑基节点、力导向节点、树图节点、箱线五数）：列装不下"每点一个小对象"，
  那类该走「索引 + 外部存储」。
- 需要编辑/写回（拖点改数据）：列存是只读快照，得有回写列或"转回对象"的路径。
- 需要快照往返：虚拟系列**不进 option 快照**，数据归应用自己的数据通道。
- 每点一个 DOM / 组件：那不是列存能救的，要虚拟列表。

## 6. 推广时的三步走模板

这次走过的顺序可以原样复用（每步都能停在"全绿"）：

1. **加适配层**：统一读点接口，用"逐字等价"的实现顶上，跑全量单测证明零行为变化。
2. **迁移调用点**：按批次（热路径 → 建模与渲染 → 其余）把所有直读写点换掉；
   顺手把逐点热循环换成标量访问器。
3. **真正不建对象数组**：在这一步才让 `points` 留空，并**同时**把不支持的用法做成显式报错。

纪律一条：**半迁移状态禁止提交**（`points` 已空而仍有站点直读，会造成静默少画 / 提示框空）。

下一步的候选顺序（有需求驱动再做）：

1. 折线 / 面积通用化（与散点同一套列，成本最低）；
2. 热力图（稠密矩阵，收益最大）；
3. 实时流的环形缓冲（把 appendData 从"全量重建"变成真增量）；
4. 分块加载（亿级数据）；
5. 与引擎虚拟源打通（列直接喂给引擎，省掉中间拷贝）。
