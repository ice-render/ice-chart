# 更新流水线的增量归一化 / 增量布局（**第 0 期已落地，P1~P4 待做**）

> 状态：**第一刀已落地**（2026-09-23，见下「第 0 期」）；P1~P4 仍未开工。
> ⚠️ 优先序已按实测**改过**：下面表里的 P1~P4 是 09-22 按推理排的，
> 实际 profile 显示大头在「类目域 / 类目索引表」（第 0 期），布局那一段只占 4%。先读第 0 期那节。
> 起因：列存 / 环形缓冲把「存储」压到 O(1) 之后，每 tick 的地板落在了
> 「**数据一变就整条重跑**」这条流水线上（归一化 + 布局 + 同步组件）。

## 1. 现在的地板是多少（实测，不是估算）

尺子已经固化成脚本：`scripts/measure-pipeline.mjs`
（页内注册一个最小自定义系列 + 1 万个类目，逐 tick 追加；`--url` 可以指向 trading 的示例页）。

| 口径（1 万根 / 10 万根窗口，真机 Chromium） | 每 tick | 其中 applyOption（流水线） |
|---|---|---|
| 惰性原始点 + **环形**追加 | **1.3 ms** | ~1.1 ms |
| 普通（concat + `setData`） | 2.4 ms | ~2.4 ms |

其中**纯存储部分**（写槽位 + 域增量 + 类目表增量）只有 **0.13 ms** ——
也就是说：存储这半已经压到 O(1)，剩下的 90% 是流水线。
普通路多出来的那一截，就是每 tick 物化 1 万个 `DataPoint` 的表示税。

## 2. 流水线今天都在做什么（事实清单）

`applyOption` → `rebuild` 的步骤，按当前成本从大到小：

1. `normalizeOption`：建点 / 轴域 / 类目表 / 堆叠 / 图例选中 / 主题合并；
2. `computeLayout`：量轴标签宽度（已按样本量）、排标题与图例、推绘图区；
3. `syncComponents`：逐组件 `updateSeries` / `setCoord` / `markDirty`；
4. 引擎：脏矩形重绘（这一层本来就不是瓶颈）。

**已经做过增量的**（0.29 – 0.30.1）：类目表、数据域、点物化、布局里的标签宽度测量。
**还没做的**：上面第 1 条的其余部分、第 2 条的全部、第 3 条的全部。
注意：`setDomain`（纯视窗变化、数据没变）走的也是同一条流水线 —— 收益不只给实时流。

## 3. 要做什么（分层，按收益排）

### 第 0 期 —— **类目域 / 类目索引表**（2026-09-23 已落地，实测收益最大）

先按**函数级 CPU profile** 拆了一遍（10 万根窗口、真机 Chromium、默认示例页当宿主），
结论与上表排的顺序不一样 —— 八成成本在归一化里的**类目域**，布局只占 4%：

| 函数（自身耗时占比） | 做什么 | 怎么收 |
|---|---|---|
| `buildXDomain` 33% | 每帧对 10 万类目重新做一遍「去重 + 首次出现顺序」 | 单一惰性原始点来源**直接复用**存储那张增量维护的表 |
| `normalizeOption` 自身 25% | 里面其实是 `resolveXDomain` 被内联了：把「全量域」当视窗传下去 → 两趟 O(n) `indexOf` | 没有真视窗就传 `null`（结果完全一致） |
| `BandScale.indices` 17% | 每个新比例尺重建一遍 10 万条的 `Map` | 存储提供 O(1) 查表口（**绝对序号 − 首项序号**），`BandScale` 不再自建 |

实测（`scripts/measure-pipeline.mjs`）：

| 口径（惰性原始点 + 环形追加） | 第 0 期前 | 第 0 期后 |
|---|---|---|
| 1 万根窗口 每 tick | 1.4 ms（其中流水线 1.47） | **0.4 ms**（0.44） |
| 10 万根窗口 每 tick | 15.0 ms（其中流水线 15.2） | **2.0 ms → 1.6 ms**（见第 1 期） |

### 第 1 期 —— **稠密轴的标签惰性格式化**（2026-09-23 已落地）

第 0 期之后 profile 重跑，地板摊成：`computeLayout` 17% + `buildAxisLayout` 13% +
`formatTick` 12% + `thinXAxisLabels` 7%。再往下拆发现**罪魁不是「布局没复用」**，
而是「每帧为 10 万个类目格式化 10 万个标签、再把 99.9% 抹掉」。

> 📌 这条对施工图的启示：**P1（布局复用）在滚动窗口这个场景里本来就帮不上忙** ——
> 数据每 tick 都变，域的判据永远不成立。真正该做的是「别做那些注定要被扔掉的工作」。
> P1 仍然值得做，但它服务的是另一个场景（纯视窗变化 / 悬停 / 无数据变化的 `setDomain`）。

做法：刻度数 > 512 的轴只格式化量宽度的样本（≤ 64 颗 + 首末），抽稀定稿后按留下的下标现算。
10 万根窗口 **2.0 ms → 1.6 ms**。专项核对过 30 / 400 / 5 000 / 50 000 个类目：
非空标签与「全量格式化再抽稀」**逐项一致（0 项不一致）**。

### 下一步（2026-09-23 收尾时的 profile，留给下一个会话）

0.30.2 之后 10 万根窗口 1.6 ms/tick，函数级摊平成了这样（自身耗时占比，200 ticks）：

| 函数 | 占比 | 说明 |
|---|---|---|
| `computeLayout` | 16.1% | 主要在建临时比例尺 + 排标题 / 图例 / 绘图区 |
| `syncComponents` | 14.0% | 逐组件 `setState` / `markDirty`，含那趟 10 万长度的 `ticks.filter` |
| `(anonymous)` | 12.4% | 未归名（怀疑是 `BandScale.ticks()` 的 `domain.slice()` 与几个大数组回调） |
| `buildAxisLayout` | 11.7% | 建表本身（已经不再格式化全量标签） |
| `thinXAxisLabels` | 6.0% | 抽稀 + 抹白那趟 O(n) 循环 |
| `removeCategory` / `tickEntries` / `measureText` | 各 4~5% | 存储淘汰、刻度映射、量文字 |

**结论：剩下的地板不是某一个热点，而是「10 万类目这个长度本身被反复搬运」** ——
临时比例尺 `slice()`、`ticks()` 再 `slice()`、抽稀抹白循环、`grid.xTicks` 的 filter、
`Axis` 遍历整表…… 每一处都是 O(n) 的小常数，加起来就是 1.6 ms。

所以真正该做的下一刀（比 P2 更靠前）是**让「轴的刻度表」本身变瘦**：
`AxisLayout.ticks` 现在恒等于「整条类目域」（10 万项），而抽稀之后真正要画的只有十几项。
把契约改成「轴的 tick 表 = 抽稀后的那些项」（值 + 原下标），`Axis` / `GridLines` /
`syncComponents` 都只遍历这十几项，上面那一整排 O(n) 就一起消失了。

⚠️ 这是一次**契约改动**，动手前先确认三处：① `Axis` 里靠
`labels.length === ticks.length` 判断「这张表抽稀过」的分支；② `GridLines` 的
`xTicks` 对齐口径；③ 现有用例里凡是断言 `ticks.length === 类目数` 的地方。
（数量不大，但它横跨 layout / Axis / GridLines 三个文件，值得单独一轮。）

### 第 2 期 —— **刻度表的热路径只走「要画的那些」**（2026-09-23 已落地）

上面那条「让 tick 表变瘦」的契约改动**没有做成**：真去读那三处守卫时发现，`ticks`（整条域）
与 `labels`（同长度、抽稀处为空串）这套形状被三处约定同时依赖，改形状要连用例一起重写。
换了个**不动契约**的做法，拿到了同样的收益：

- `AxisLayout` 增加 `visible: number[]` = 抽稀后仍要画的原下标（`undefined` = 没抽稀、整表都要画）；
- `Axis` 与 `grid.xTicks` 改成按 `visible` 遍历 —— 10 万类目的轴从「每帧扫 10 万项」变成「扫十几项」；
- 惰性形态的「抹白」只处理样本（≤ 64 颗），不再扫整张 10 万项的表；
- `ticks` / `labels` 的长度与对齐关系**保持原样** → **486 个用例一行没改**就全绿。

实测：1 万根窗口 **0.4 ms → 0.2 ms**、10 万根 **1.6 ms → 0.6 ms**（p50，含流水线）。
等价性核对（40 / 900 / 20 000 个类目）：`visible` 是真子集、三者计数一致、
与「扫整表」参照**逐项 0 项不一致**。

> 📌 这一期还带出一条**必须记住的教训**：`audit:interactions` **不是稳定门禁**。
> 拿未含本次改动的基线连跑 3 次，**3/3 全失败**（`dashboard` / `dashboard-logistics` 的
> `ink-over-right-axis`，都在「布局几何变了」的步骤上）—— 也就是说这条门禁在 0.30.2 的
> main 上就是红的，只是偶尔通过。**不要再用单次运行的结果当"全绿"的证据。**
> 它和脚本里已登记的 `editable-chart` 已知问题同类（缺「布局变化 → 整帧重绘」），待立项。

### 第 3 期 —— **视窗裁剪下的类目查表**（2026-09-24 已落地）

第 0 期交出去的查表口有一个**前提**：只有「域原样来自那张表、没被视窗裁剪」时才给 ——
因为查表口是按**整张表**编号的。滚动看盘（轴的域是整张表的一段）正好落在这个前提之外，
于是**每次追加都退回去自建索引表**：10 万类目 ≈ 1ms/次 × 每 tick 两趟重建（追加一趟、
推视窗一趟）。函数级 profile 里它就是 `indices` 那一项（3 秒 214.7ms，7%）。

做法（不破任何契约）：查表口**照交**，再给一个 `categoryOffset` = 「域起点在整张表里的下标」，
`BandScale.indexOf` 用「全表下标 − 偏移」换算窗口内下标（越界就是不认，语义与自建表一致）。
顺带把同一口径铺到三处原本的全表 `indexOf`：`resolveXDomain`（两趟 O(n)）、
`domainFractions`、`clampAxisDomain` —— 有查表口就走 O(1)，没有的还是老路。

实测（`scripts/measure-pipeline.mjs` 新增一档「惰性原始点 + 环形 + **视窗**」，
宿主是 ice-trading-chart 的流式页，真机 Chromium）：

| 口径（惰性原始点 + 环形 + 视窗） | 第 3 期前 | 第 3 期后 |
|---|---|---|
| 1 万点 每 tick p50 | 0.5 ms（流水线 0.22） | **0.2 ms**（0.11） |
| 10 万点 每 tick p50 | **1.6 ms**（流水线 1.48） | **0.3 ms**（0.34） |

不带视窗的档位**没变**（0.6 ms @ 10 万，两版一致）—— 它本来就走查表口，这条改动
只是把「同一个能力」补到有视窗的场景；「普通（concat + 重建）」那档也没变（21 ms，那是另一条路）。

等价性：`tests/scale/scale.test.ts` 锁住「全表下标 − 偏移」的换算与越界不认；
`tests/chart/stream.test.ts` 锁住「视窗裁剪后查表口仍在 + 映射与自建表逐点一致」。

### 第 4 期 —— **一次更新一遍归一化**（2026-09-24 已落地）

第 3 期之后，**普通（非列存）系列**仍然是「一次更新两遍归一化」：`applyOption` 一遍
（全域：主题 / 全域域 / 隐藏集合 / dataZoom 初始窗口），`rebuild` 一遍（视窗域）。
第二遍的全部作用只是把视窗**套**上去 —— 而视窗在归一化里只落在三处：
① x 域裁剪（`resolveXDomain`）；② y 轴显式域；③ 表达式系列的采样区间。

做法（不破任何契约）：新增纯函数 `applyViewToNormalized(norm, view)` —— 把全域那遍的结果
套上视窗，与 `normalizeOption(option, view)` **逐项一致**；`canApplyView` 挡下算不对的两种
（表达式系列 / 等比坐标：采样区间与轴跨度都由视窗决定，只能整条重跑）。

| 口径（普通系列，10 万点 / 1 万点） | 改前 | 改后 |
|---|---|---|
| `measure-pipeline.mjs` 每 tick p50 | 10.5 / 2.2 ms | **7.8 / 1.1 ms** |
| 单测拆解：`setData` | 6.2 ms | **3.6 ms** |
| 单测拆解：`setData` + 调用方 concat/slice | 9.4 ms | 7.0 ms |
| 纯视窗 `setDomain`（本来就只一遍） | 3.2 ms | 3.4 ms（噪声内，不变） |

惰性原始点 + 环形（±视窗）两档**一个字节没变**（0.6 / 0.3 ms）—— 它们本来就没走第二遍。

门禁：`tests/option/apply-view.test.ts`（等价性；含「横向图 / 热力图的**类目 y 轴不吃
y 视窗**」这条被集成用例先抓出来的规矩）、`tests/chart/single-normalize.test.ts`
（调用计数：`setData` / `setOption` / `appendData` / `setDomain` 各一遍）。

⚠️ 这一期还**证伪了一条推断**：滑动窗口的数组拷贝不是成本。10 万点上
`concat` + `slice(-n)` 只有 **0.055 ms**（原地 `push` + `splice(0,1)` 0.005 ms）——
按「少搬一趟」把 `appendData` 改成原地追加，实测买不到性能，却会改掉**调用方自己那个
数组**（调用方普遍留着引用）。已退回，契约锁在 `tests/chart/append-array-contract.test.ts`。

**下一条（普通路径剩下的大头）：类目域的增量重建。** 普通系列只要「类目变了」
（滑动窗口 = 每 tick 都在变）就要把 10 万类目重新去重一遍：同数组 `setData` 4.0 ms
vs 滑动窗口 7.5 ms；数值轴对照 3.5 vs 3.2（**没有类目可重建就没有这笔**）。
这正是 0.30.8「还剩什么」留下的那条账，范围从「多来源合并」扩到「单来源的追加 / 淘汰」。

### 第 5 期 —— **单来源普通系列的增量类目域**（2026-09-24 已落地）

第 4 期之后，10 万点普通系列的真滑窗仍有 7.8ms/tick，函数级 profile 的第一名就是
`buildXDomain`（**自身 38.7%**，实测 2.9ms/tick）：每 tick 把 10 万类目重新去重一遍，
还要顺带建一张 10 万条的 `Map`（这张表同时当查表口交给 `BandScale`）。

做法（照 `SeriesRawPoints` 那套已经跑熟的**绝对序号**口径，不另发明一套）：

1. **缓存键按数据数组身份**（顺带修掉一条真 bug）：普通系列原来只按「点数 + 首末 x」记键，
   「长度、首、末都没变、中间变了」会命中**过期的域**（类目轴上凭空少/多一个类目，且不自愈）。
   现在把数组身份记进键，轴自己声明的 `axis.data` 同样处理。
2. **单来源普通系列维护一张增量类目表**（图表实例缓存上）：`values`（上一次的 x 值序列）
   + `seq`（类目 → **绝对序号**，下标 = 序号 − 首项序号）。滚动窗口只做「删头 / 补尾」，
   各 O(delta)。
3. **逐项验过才认**：拿上一次的 x 值序列与这一次逐项比同一性（不做字符串转换），
   对不上 / 出现重复类目 / 换了数据源 / 换了系列 → 退回全量聚合（**宁可多算一次，不给错的轴**）。
4. **退回全量那条路复用聚合那趟的 `seen` 与类目数组**当新状态：否则「验证不过」的每一帧
   都会白建一张 10 万条的 Map（实测 +2.3ms/tick —— 这正是本轮先跑出 9.8ms 再修掉的那一笔）。
5. **尾部被裁掉时把序号压回去**（`next = 最后一个存活序号 + 1`）：不压就会留下**空洞**，
   而「下标 = 序号 − 首项序号」在空洞之后会整体偏大 —— `BandScale` 一看越界就判「不在域里」，
   那些柱子 / 点**直接不画**。踩到的形状是「窗口先变短、再追加一项」
   （门禁：`tests/option/category-domain-cache.test.ts` 的「窗口先变短、再追加」那条）。

| 口径（10 万点普通系列，每 tick p50） | 第 4 期后 | 第 5 期后 |
|---|---|---|
| 真滑窗（头部淘汰 + 尾部追加） | 7.8 ms | **4.2 ms** |
| 1 万点真滑窗 | 1.1 ms | 0.9 ms |
| 头部不动、只换尾巴（验证不过 → 退回全量） | 7.55 ms | 7.07 ms（不退化） |
| 惰性原始点 + 环形（±视窗） | 0.5 / 0.3 ms | 0.5 / 0.3 ms（不变） |

profile（真滑窗，100 ticks）：`buildXDomain` 掉出榜单，`tryIncrementalCategoryDomain` 只占
**4.2%**；剩下的 54% 是**点物化 + GC**（`readGenericPointInto` 19.7% / `buildPoints` 17.8% /
GC 16.7%）—— 下一条就是它（P2/P3 的「增量点物化」）。

门禁：`tests/option/category-domain-cache.test.ts`（三条过期域用例 + 两条滑动窗口等价性护栏；
把逐项校验去掉会立刻红 —— 已实测）、`tests/option/raw-category-index.test.ts`（存储那张表的同一不变式）。

**多来源也吃到了（同一轮补的）**：K 线 + 量柱 + 均线共用**同一批 x** 时，先算第一条的增量表，
再逐项验证其余来源与它同一 —— 同一就直接用那张表（`sourcesMatchDomain`），不必每帧再合并。
10 万点 3 系列、同帧批更新（`setOption` 一次带全部系列）：**16.5 → 11.4 ms/tick**
（同一版本里「把增量状态清空、强制全量合并」的对照）。

⚠️ **但「多个系列各自 `setData`」那条路帮不上**：喂数据是一系列一次的时候，
中间态里各系列本来就不对齐（第一条已经滑过去了，第二三条还没），**逐项同一永远不成立**。
那条路用既有的 `series[i].xFrom` 声明（框架据此把派生系列摘出合并）：实测 3 系列 10 万点
**51.8 → 28.5 ms/tick**；改成同帧批更新是 10 ms/tick 一档。真正想根治得做 P4（同帧批合并）。

真正**完全不同**的多个来源（各自的类目表不一样）仍然每帧全量合并 —— 那要按
「每来源一张增量表 + 并集增量」做，工作量大一档，另行立项。

### 第 6 期 —— **同帧批合并（P4）**（2026-09-24 已落地）

第 5 期之后还剩一种贵法：**一帧里对多个系列各自 `setData`**。实测 10 万点 × 3 系列是
**45.4ms/tick** —— 每次调用都跑一整条流水线；而且中间态里各系列天然不对齐
（第一条已经滑过去、第二三条还没），第 5 期那套「逐项同一」的增量因此也用不上。
这是**用法**带来的成本，不是某一处慢。

做法：新增 `chart.batch(fn)`（同帧批合并）。批内 `setData` / `appendData` 只改数据 + 记账，
出批（回到最外层）时跑**一次** `applyOption`，然后按调用顺序补发 `data:change`。

三条语义（测试锁住）：① `batch()` 返回时图表已经是新状态（**同步**，不是「下一帧生效」）；
② 批内不发布事件、出批后补发 —— 监听者读到的图永远自洽；③ 批内抛异常也 flush（`finally`）。
动画标志取**与**：批内只要有一次不要动画（滑动窗口的 `appendData` 默认就是），整批都不插值。
批内的 `setOption` / `setDomain` 照旧立即生效（批合并只作用于数据更新）。

| 口径（10 万点 × 3 系列滑动窗口，每 tick p50） | 改前 | 改后 |
|---|---|---|
| 逐系列 `setData` | 45.4 ms | **10.4 ms**（包进 `batch()`） |
| 逐系列 `setData` + `xFrom` + `batch()` | — | 9.9 ms（这条路上 `xFrom` 已非必需） |
| 同帧批 `setOption`（一次带全部系列） | 16.5 ms | 11.4 ms（第 5 期的多来源增量） |

门禁：`tests/chart/batch.test.ts`（一遍归一化 / 同步语义 / 事件时序 / 异常 flush / 嵌套批 /
批外不变）+ 全套回归 + `audit:interactions` + `audit:hover`。

### 第 7 期 —— **只换视窗不重建点集**（2026-09-24 已落地）

P2 剩下最容易的一刀：`buildPoints` 每趟归一化都要给每个普通系列物化一遍 `DataPoint`，
而**平移 / 缩放 / 重复归一化时数据根本没变**。做法与类目域那套同源（判据＝
**数据数组身份 + 长度 + 解析规则** `type|xField|yField`），命中就整批复用。

| 口径（10 万点普通折线） | 改前 | 改后 |
|---|---|---|
| 只换视窗（平移 / 缩放） | 3.4 ms/tick | **1.0 ms/tick** |
| 滑动窗口（每 tick 换新数组） | 4.5 ms/tick | 4.5 ms/tick（**不复用**，符合预期） |

未做（有意）：**增量**复用（只追加 / 只淘汰时复用重叠部分的点对象）—— 那要把复用点的
`index` 重编号，等于让「上一帧的 `norm`」看到被改过的点对象。收益（10 万点滑窗约 1.5ms，
且该场景的帧由光栅主导）不值这个语义代价。要做就得先定「点对象可以跨帧共享」的契约。

#### ⚠️ 帧 ≠ 流水线：上面那 54% 是**流水线内**的比例（2026-09-24 实测）

把尺子换成「真实帧」（数据更新 + 渲染；10 万点普通折线、类目轴、真滑窗）之后账完全变形：

| 口径 | 数 |
|---|---|
| 帧间隔 p50 | **61 ~ 70 ms**（≈15fps） |
| 其中 `setData`（整条流水线） | 7.5 ms |
| 把 `doRender` 置空 | **16.6 ms（60fps）** |
| 同数据 / 同画布 / 同线段数的**虚拟（列存）折线** | 16.7 ms（60fps） |
| 同样点集但去掉 `rebuildPixels` | 57 ms（只省 4ms） |

结论：**缺口全在「画」这一步**，点物化 + GC 那 2ms 在这个场景里根本看不见。已实测排除、
别再重跑的原因：

- **不是顶点数**：真实 2094 个点，虚拟 2585 个点。
- **不是路径总长**：真实 300,892 px、虚拟 **318,702 px** —— 虚拟更长却快 3.7 倍。
- **不是颜色 / 透明度 / 重绘面积**：strokeStyle 本来就是纯色 `#0D6EFD`、alpha=1；
  两边每帧都 `clearRect(0,0,1100,460)`，clip 次数也一样（14.8 / 14.3）。
- **不是几何极端度**：真实点集的「反向次数 / 最大斜率」（860 / 432）比合成锯齿（2092 / 695）
  更温和，而那条合成锯齿在同一个组件、同一个引擎上**是 60fps**。
- **不是取点策略**：把普通折线的取点换成虚拟那套「按像素列聚合」后**更慢**（148ms）。

接着追的话**别再用 CPU profile 的 `(program)` 当线索**（那是「没有 JS 在栈上」的统称）：
换 CDP `Tracing` 的 `RasterTask` / `Paint` / `Commit` 事件看真实光栅分片，或者直接对
引擎的重绘策略立项（与 1M 那档「剩下的一半是光栅」同源）。

**已经试过的三种取点策略，都别再试**（同一份数据、同一张画布、10 万点普通折线真滑窗，
把 `renderSequence` 换掉、其余一律不动）：

| 取点策略 | 绘制点数 | 帧间隔 p50 |
|---|---|---|
| **LTTB（现状）** | 2094 | **61 ms** |
| 按像素列聚合「首 / 最低 / 最高 / 末」 | 3552 | 124 ms |
| 按像素列只画「最低 → 最高」 | 2094 | 149 ms |

也就是说：**LTTB 在这个场景里已经是这几种里最快的**，换更「省」的画法反而更慢
（成本跟着被描边的几何走，不是顶点数也不是路径总长 —— 上面第一版按列聚合还是用 Map + sort
每帧在 JS 里烧掉的，第二版才是干净的对照）。**建议不要再在本层折腾取点策略**，
要么换 CDP `Tracing` 定位光栅分片，要么直接立项引擎的重绘策略。

给用户的可操作结论：**10 万点级别的折线请开 `virtual: true`** —— 同一份数据同一张画布，
普通折线 61ms/帧、虚拟（列存）折线 **16.7ms/帧**（实测，见本节表格）。

### 下一步（第 2 期之后的起点）

剩下的 0.6 ms 里已经没有一个「10 万长度」的大头了；接着该看的是 **P2（组件同步的差异更新）**
与 **P4（同帧批合并）**，以及上面那条 `audit:interactions` 的稳定性立项
（它现在是"偶尔红"，会让后面每次改动的判定都不可靠）。

⚠️ 与 §1 / §4 里那个「1.3 ms」的口径要分清：那是 **1 万根窗口**的数，
10 万根窗口当时的实际值是 **15 ms** 量级（本机复测）。§4 的验收线（≤0.5 ms @ 10 万）
按 10 万口径还没达到，见下。

**下一步的地板（profile 已给出，就在这张表里）**：剩下的 2.0 ms 摊平在
`computeLayout` 17% + `buildAxisLayout` 13% + `syncComponents` 12% + `formatTick` 12% +
`thinXAxisLabels` 7% —— 也就是说 **P1 / P2 现在才轮到排在前面**（原先它们排第一是对的，
但那是"没量过"的推理；量过之后先做了第 0 期）。

纪律（2026-09-24 更新）：查表口**连同 `categoryOffset`** 一起交出去 ——
域是整张表的一段时靠偏移换算窗口内下标（第 3 期），所以「被视窗裁剪」不再需要退回自建表；
增量索引表 ≡ 「在类目数组里找第一次出现」这条不变式由
`tests/option/raw-category-index.test.ts` 锁着（含中途淘汰留下的**序号空洞**）。

| 期 | 内容 | 判据 / 做法 |
|---|---|---|
| P1 | **布局复用** | 轴 domain + ticks + 标签集合 + 画布尺寸全都没变 → 跳过 `computeLayout`（或只重算变了的那一轴） |
| P2 | **组件同步的差异更新** | `updateSeries` 时区分「尾部追加 / 环形滑动 / 整体替换」：前两种保留组件内的像素缓存、列存、尺寸范围 |
| P3 | **归一化的结构性跳过** | 把 `buildYDomain` 这类「有域提示就用、没有才扫」的口径铺满（列存那条路已经做到一部分） |
| P4 | **同帧批合并** | 同一帧里多次 `setData` / `appendData` 合并成一次归一化（现在每次调用都跑一遍整条） |

## 4. 验收（做到哪一档算数）

- 10 万根窗口逐 tick 追加：端到端 **≤ 0.5 ms/tick**。
  （2026-09-23 复测口径：当时是 **15.0 ms**；第 0 期之后 **2.0 ms**；1 万根窗口 0.4 ms。
  原文写的「1.3 ~ 1.7 ms」是 **1 万根** 的数，不是 10 万的 —— 已在 §3 更正。）
- **不许为了增量改变语义**：归一化仍是纯函数、快照仍以 option 为唯一事实来源、
  普通（非列存）系列的像素与既有测试逐条不变；
- 门禁：`verify:full` + `audit:interactions` + `audit:hover` 全绿，
  并把 `scripts/measure-pipeline.mjs` 的前后数字写进 CHANGELOG。

## 5. 风险与「不做什么」

- **归一化是纯函数**（见 `AGENTS.md` 的架构分层）：增量只能做成
  「输入指纹 + 复用上一次结果」，**不许**把可变状态塞进归一化 —— 那会把可单测性弄丢。
- **布局与标签耦合**：抽稀（`thinXAxisLabels`）只能在绘图区算完之后做，
  P1 的判据必须**包含标签集合**，否则会重演「标签糊成一条色带」那个坑。
- 不做：把归一化改成有状态的类；为了性能牺牲「快照 = option 快照」这条序列化契约。
