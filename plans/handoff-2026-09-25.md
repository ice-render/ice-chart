## 5. DSL 同步：已闭环（0.6.5，2026-09-25）

`calendar` / `alluvial` 已经进 `ice-chart-dsl` 的编译清单，**这一节没有待办**；留着是为了让下一个人
知道「当时怎么定的」与「哪条路走不通」，不必重新推一遍。

### 定下来的 encoding 形态（该仓 README 的 kind 表已同步）

**列名一律写在 `encoding` 里，观感配置走各自顶层的同名字段**：

| kind | 通道 | 顶层观感字段 |
|---|---|---|
| `calendar` | `encoding.x` = 日期列、`encoding.y` = 数值列（一行一天） | `calendar: { weekStart?, weekdayLabels?, monthLabels?, minColor?, maxColor? }` |
| `alluvial` | `encoding.axes` = 轴列名数组（≥2，按顺序）、`encoding.value` = 流量列（可选） | `alluvial: { sort?, spread?, nodeWidth?, gap?, ribbonOpacity? }` |

**为什么不照抄 core 的字段名**：core 的 `alluvial.rows` 是**记录对象数组**（`row[轴列名]`），
而用户手上是 `{ columns, rows }` 的两维表 —— 把「表 → 记录对象」这个转换放在编译期，
DSL 才真在做数据绑定；写成 `options.alluvial.axes` + 表整块透传就等于把绑定责任推回给调用方，
撞该仓铁律 1（不做 ChartOption 的马甲）。日历同理：**日期不在 DSL 里解析**，
core 的归一化是唯一事实来源（UTC 的 Y/M/D、同日取和），所以 `Date` 与 `2026-1-5` 都还能用。

### 诊断（口径：报 core 会**静默跳过**的那批数据）

- 错误：`alluvial-axes-too-few`（轴 < 2）、`invalid-axes`（`axes` 写成单个列名）、
  `unknown-column`（轴列不存在，带可用列名）、日历缺数值列；
- 警告：`calendar-unparseable-date`（带行数 + 建议 `YYYY-MM-DD`）、
  `alluvial-single-category`（单类目轴 = 一条直线）、`alluvial-missing-axis-value`
  （正是 core 会跳过的那批行）。
  日期判据**故意比 core 宽松**（只做它的兜底那一步 `Date.parse`），方向单向：DSL 说「不像」的，
  core 一定也读不出来 —— 宁可漏报不可误报。
