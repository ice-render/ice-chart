# 列存（虚拟）系列：把百万级数据从「对象数组」里拿出来

> 状态：**已实现**（`series.virtual: true`，覆盖散点 / 折线 / 面积 / 热力图，2026-09-21）。
> 本文记录机制、对外契约、实测账，以及**可复用边界** —— 以后要把它推广到折线 / 热力图 /
> 实时流 / 引擎虚拟源，先读这一篇，不要重新调研。
>
> 相关的施工记录与验收数据在 `plans/scatter-large-data-virtualization.md`，
> 仓库内的改动纪律在 `AGENTS.md` 的「虚拟（列存）系列」一节。

## 1. 问题：不是"画得慢"，是"表示得贵"

100 万散点在默认视图下**全部可见**（1M 个点挤进 960px）。最初的判断是"绘制太慢"，
于是做了可见窗口裁剪与密度抽稀（每像素列约 2 点）—— 平移从 472.7ms/帧降到 8.4ms。
但内存账没动，拆开看是这样：

| 账单 | 100 万点的占用（量级估算，总账见 §4 的实测） |
|---|---|
| 原始数据项（`[x, y]` 元组，每点一个数组） | 40 ~ 70 MB |
| 归一化产出的 `DataPoint`（每点一个对象） | ~50 MB |
| 运行期按点缓存（`pixels` 2n + `effective` 2n + `itemProgress` n） | 40 MB |

**真正的大头是"每点一个对象的表示税"**，渲染只是把这份账单付到台面上。
所以这次动的不是绘制代码，是数据的**表示形态**：数据以列（`Float64Array`）为准，
`DataPoint` 退化成"要看某个点时临时合成的视图"。

## 2. 机制：六条可迁移的原则

只有第 1 条与"散点"绑定，其余五条是通用的 —— 这才是本文值得沉淀的部分。

1. **值与表示解耦**：列是事实来源，数据点对象是按需合成的视图，不再常驻。
2. **读点收敛到统一入口**：数量走 `pointCount`，取点走 `pointAt(i)`，
   逐点热循环走标量访问器（`xValueAt / yValueAt / baseAt / topAt / sizeAt`）。
   入口统一之后，**换存储形态是局部改动，不是全仓重写** —— 这是这次最大的一笔架构红利。
3. **热的与冷的分开**：逐点绘制/插值的循环只取标量（不合成对象）；
   提示框、无障碍镜像、事件参数这些"每次只有一两个点"的冷路径才合成对象。
4. **全量缓存 → 按需重算 + 二分定位**：`pixels`（2n）这类"以空间换查询"的默认策略，
   在点数超过阈值后换成"以计算换空间"，并用二分/索引把计算压到 O(log n)。
5. **数据域 / 单调性 / 尺寸范围与建列同一趟算完**：后续任何环节都不再扫全量数据。
   每多扫一遍 100 万点就是几毫秒，而且中间产物会立刻被丢弃。
6. **不支持的用法显式报错**：宁可抛错，也不要"静默少画 / 空提示框 / 悄悄降级"。
   语义边界写进类型文档（见 `src/types.ts` 的 `virtual`）。

## 3. 对外接口

```js
// 推荐：直接给列（Float64Array 会被直接采用，不再复制一份）
series: [{ type: 'scatter', virtual: true, data: { x: Float64Array, y: Float64Array } }]
series: [{ type: 'line',    virtual: true, data: { x, y }, lineWidth: 1 }]
series: [{ type: 'area',    virtual: true, data: { x, y } }]

// 热力图走**稠密矩阵**：行列类目 + 行优先的值矩阵（NaN = 空格）
series: [{
  type: 'heatmap', virtual: true,
  data: { xCategories: ['c0', 'c1', ...], yCategories: ['r0', ...], values: Float64Array },
}]

// 实时流：同一个 appendData，但追加进的是**环形缓冲**（maxPoints = 滑动窗口大小）
chart.appendData('line', [[t, value]], { maxPoints: 20000 });

// 亿级数据：分块按需加载（只驻留可见窗口覆盖的块）
series: [{
  type: 'line', virtual: true,
  data: {
    sizes: [1_000_000, 1_000_000, /* … 1 万块 = 100 亿点也行 */],
    rangeOf: (i) => [i * 1e6, (i + 1) * 1e6 - 1],   // 声明式块范围：定位不用先加载
    yDomain: [0, 100],                              // 声明式值域：坐标轴不随加载漂移
    loadChunk: async (i) => ({ x, y }),             // 同步或异步；异步到货自动重绘
    maxResidentChunks: 4,                           // 常驻上限（LRU）
  },
}]

// 把列交给引擎的虚拟层（列不复制；命中即物化、SVG 导出等能力来自引擎）
const source = chart.createVirtualSource('big');
ice.addChild(new ICEVirtualLayer({
  left: chart.layout.plot.x, top: chart.layout.plot.y,
  width: chart.layout.plot.width, height: chart.layout.plot.height,
  childSource: source,
}));

// 也收：元组数组（适合几十万级、应用侧本来就是数组的场景）
series: [{ type: 'scatter', virtual: true, data: [[0, 1], [1, 3], ...] }]

// 也收：纯数值数组（x 取下标）
series: [{ type: 'scatter', virtual: true, data: [1, 3, 5, ...] }]
```

内部契约（改数据点存储 / 命中路径前必读，与 `AGENTS.md` 同步）：

- **读点只有三个入口**：`pointCount` / `pointAt(i)`（断点仍是 `y: null`）/ 标量访问器。
  虚拟系列的 `points` 是**空数组**，直读 `points[i]` 会静默少画。
- **归一化后释放原始 `data`**：建完列就把 `option.series[i]` 换成不含 data 的副本
  （百万级元组本身就要 40~70MB）。列存缓存在图表实例上，供同一轮的第二遍归一化复用。
- **不物化按点缓存**：虚拟系列不建 `pixels` / `effective` / `itemProgress`；
  渲染与命中都从「列 + 同一份比例尺」现算 —— **同一个公式、同一份数据**，
  不存在"两套坐标"的分叉。这是 `AGENTS.md` 铁律 2（像素缓存唯一）的唯一例外。
- **共用内核在 `SeriesBase`**：`syncVirtualMeta` / `virtualVisibleWindow` / `virtualPixelAt` /
  `virtualNearestIndexAtX`。各类型的差异只有「窗口怎么画出来」：
  散点是密度抽稀后逐点画；折线 / 面积按**像素列**分桶保留「首 / 最低 / 最高 / 末」四点 ——
  每列最多 4 个点，尖峰不会被采样吃掉（折线丢掉极值就是撒谎）。
- **冷路径也不许全量扫**：交互窗口兜底（`numericXProbe`）改成在单调列上二分，
  无障碍数据表默认封顶 200 行（超限按等步长抽样并在 caption 写明）。
  新增"看一眼就完"的消费方之前先问：这件事需要知道**每一个点**吗？
- **热力图的形态是矩阵，不是点集**（`SeriesGrid`）：行列由类目定死，值按行优先排进
  `Float64Array`。于是三件事一起变简单：内存（100 万格 8MB）、**命中 O(1)**（类目查表 + 下标运算，
  不再是「逐格比矩形」）、绘制可以按窗口裁剪；亚像素时按**屏幕像素块聚合**（块内取最大值，
  热点不被抹平），聚合结果按几何键缓存。稀疏数据不要用矩阵（归一化会按密度报错）。
- **实时流是环形缓冲**（`SeriesRing`）：`appendData(id, items, { maxPoints: 窗口 })` 在虚拟
  数值列系列上不再 concat + 全量重建，而是「写 1 个槽位 + 挪一次起点」。
  与连续列是同一件事的两种物理布局，所以**共用同一组访问器** ——
  但它的物理下标 ≠ 逻辑下标，直读 `ring.x[i]` 会在绕回之后读到别的点。
- **亿级数据是分块按需加载**（`SeriesChunks`）：`data: { sizes, rangeOf, yDomain, loadChunk }`，
  图表只让「可见窗口覆盖的块」驻留（`maxResidentChunks`，LRU），未驻留的点读出来是「没有值」。
  两条声明式要求不是洁癖：`rangeOf` 让窗口定位**不必先加载**，`yDomain` 让坐标轴**不随加载漂移**
  （亿级数据不可能为了自动缩放把块全 load 一遍）。
  另有一条实测教训：窗口覆盖的块数远大于驻留预算时，**不能对窗口内每块都发请求** ——
  10 亿点缩到全量视图时窗口覆盖 1 万块，全请求 = 1 万次加载（初始化 22 秒），
  现在按预算**均匀取样**（3 次、3ms），与散点/折线的密度抽稀是同一条思路。
- **列可以直接交给引擎的虚拟子源**：`chart.createVirtualSource(seriesId)` 返回一个
  `VirtualChildSource`（坐标是组件本地 = 绘图区像素，与引擎「容器局部」口径一致），
  把 `ICEVirtualLayer` 摆在绘图区上就能让**引擎**负责窗口裁剪 / 批量落墨 / 命中，
  并白拿引擎侧的能力：**命中即物化**（点一下变成可拖的真图元）、SVG 导出、
  worker 镜像告警、对齐参考线。数据**不复制**，引擎读的就是图表那几条列。

## 4. 实测

同一把尺子、同一台机器、真机 Chromium、100 万点（普通路给元组，虚拟路给列）：

| 口径 | 普通（元组 + DataPoint） | 虚拟（列存） |
|---|---|---|
| 堆（CDP 取堆，GC 后） | 125.2 MB | **2.2 MB** |
| `points.length` / `pointCount` | 1,000,000 / 1,000,000 | **0** / 1,000,000 |
| `pixels.length` | 2,000,000 | **0** |
| 命中 p50 / p95 | 0.8 ms / 1.1 ms | **0.00 ms / 0.00 ms** |
| 平移 p50 / p95（60 帧拖拽） | 16.7 ms / 17.5 ms | 16.7 ms / 17.4 ms（都在 60fps 上限） |
| 交互窗口兜底（滑块每步） | 63.9 ms | **10.8 ms**（剩下的是同步重渲染；兜底本身已经是 O(log n)） |
| 构建 | 752 ms | 640 ms |

折线（同 100 万点）走同一条路：堆 125.8MB → **2.6MB**、命中 0.8ms → **0.00ms**、
交互窗口兜底 62.3ms → **10.8ms**。

热力图（同一台机器，同尺寸对照取 200 × 200 = 4 万格）：

| 口径 | 普通（元组 + DataPoint） | 列存（矩阵） |
|---|---|---|
| 堆 | 7.0 MB | **2.9 MB** |
| 命中 p50 / p95 | 6.8 ms / 9.2 ms | **0.00 ms / 0.10 ms** |
| 单步重算（滑块） | 1.63 ms | 0.43 ms |

列存热力图**不受尺寸拖累**：1000 × 1000 = 100 万格时堆 3.3MB、命中 0.00ms、单步重算 3.02ms
（重算就是那一趟按块聚合）。普通路 100 万格**跑不完**：它的命中与绘制都是逐格线性，
每格还要线性查一次类目（4 万格时单次命中已经 6.8ms，1M 格按线性外推是几百毫秒量级）。

实时流（同一个 `appendData` + `{ maxPoints }`，单系列逐点追加，p50 / p95）：

| 窗口 | 普通（concat + 全量重建） | 列存（环形缓冲） |
|---|---|---|
| 1,500 | 0.30 / 0.90 ms | **0.10 / 0.40 ms** |
| 20,000 | 0.80 / 2.90 ms | **0.20 / 0.50 ms** |
| 100,000 | 5.80 / 15.10 ms | **0.40 / 0.70 ms** |

普通路的成本随窗口线性长（10 万点时 p95 15.1ms，一帧预算基本吃光），
环形缓冲几乎与窗口无关 —— 60Hz 实时流的可用窗口从「几千点」抬到「十万点」。

分块加载（10 亿逻辑点 / 1 万块 × 10 万点，`maxResidentChunks: 3`）：

| 口径 | 实测 |
|---|---|
| 逻辑点数 | **1,000,000,000** |
| 常驻块（内存的真实占用） | **3**（30 万点 ≈ 4.8MB 列） |
| 初始化 | **3 ms**（只登记块长度 / 范围 / 值域，不加载任何块） |
| 加载次数 | **3**（按预算均匀取样；修之前是 1 万次、初始化 22 秒） |
| 堆（CDP 取堆，GC 后） | **2.7 MB** |
| 平移到 9 亿点处 | 换一批块驻留，常驻数不变、堆不变 |
| 数据点对象 | 0 |

把列交给引擎虚拟层（100 万点散点，`chart.createVirtualSource`）：
落墨 **2.1ms/帧**、命中 p50/p95 **0.00ms**、堆 **2.1MB**、物化子项 0。
`forEachInBox` 是 O(窗口项数)（全窗 100 万项约 30ms）——它服务的是**按需**的窗口物化 /
对齐参考线，别每帧全窗调用。

示例页：`examples/large-data-virtual-series.html` —— 一张散点 + 一条折线**共用同一份列**，
页面里的状态行实时显示点数、数据点对象数、像素缓存长度、折线实际绘制的点数与堆占用。

## 5. 复用边界：哪些场景值得用

**判定规则**：`每点的"表示税" × 点数` 是否已经超过你愿意为交互延迟付出的重算成本。
经验阈值：**>10 万点**、或**每点内存 >50 字节**、或**必须与视口解耦**（不管放大到哪都要能拖）。

| 场景 | 为什么契合 | 还差什么 |
|---|---|---|
| 折线 / 面积（监控、长历史、科学曲线） | 与散点同一套 (x, y)，收益相同 | ✅ 已落地（共用虚拟内核；折线按像素列保留极值） |
| K 线 / 看盘类 | tick 级数据、缩放平移最频繁、多 pane 联动回显，"回到最新 N 根"天然是百万级窗口操作 | 一行多条列（OHLCV）+ 历史分页加载 |
| 热力图 | 本质是 rows×cols 的稠密矩阵（1000×1000 就是 100 万格） | ✅ 已落地（`SeriesGrid` 矩阵；命中 O(1)、亚像素按块聚合） |
| 实时流（数据 append） | 每 tick 全量重建的窗口上限只有几千点 | ✅ 已落地（`SeriesRing`：10 万点窗口 0.40ms/次） |
| 亿级数据 | 内存必须与数据总量解耦 | ✅ 已落地（`SeriesChunks`：10 亿逻辑点 / 常驻 3 块 / 堆 2.7MB） |
| 列式数据源对接 | 与列式格式（Apache Arrow / Parquet 这类）的内存布局同构，可以像今天"直接采用 Float64Array"一样直接采用 | 输入适配层（成本很低） |
| Worker / GPU 路线 | `Float64Array` 可 zero-copy 转移给 Worker；同一条列也能直接上传成 GPU 顶点缓冲 —— 对象数组做不到 | 主线程只画、Worker 算的管线 |
| 引擎虚拟源 | 引擎侧已有虚拟子源（`VirtualChildSource` + `ICEVirtualLayer`） | ✅ 已落地（`chart.createVirtualSource(id)`：列不复制，命中即物化 / SVG 导出 / 对齐参考线归引擎） |
| 无障碍镜像 / 节点列表 | 现在每系列最多建 200 个节点，就是因为 100 万节点会爆；列存 + 窗口化后可以只给视口内的点建节点 | 视口变化时增量增删 |

**什么时候别用**（列存救不了，或者反而更贵）：

- 数据量小（几万以内）：多一层间接，冷读还要合成对象，收益为负 —— 所以默认关闭、显式开启。
- 每个点带独立语义小结构（桑基节点、力导向节点、树图节点、箱线五数）：列装不下"每点一个小对象"，
  那类该走「索引 + 外部存储」。
- 需要编辑/写回（拖点改数据）：列存是只读快照，得有回写列或"转回对象"的路径。
- 需要快照往返：虚拟系列**不进 option 快照**，数据归应用自己的数据通道。
- 每点一个 DOM / 组件：那不是列存能救的，要虚拟列表。

## 6. 推广时的三步走模板

这次走过的顺序可以原样复用（每步都能停在"全绿"）：

1. **加适配层**：统一读点接口，用"逐字等价"的实现顶上，跑全量单测证明零行为变化。
2. **迁移调用点**：按批次（热路径 → 建模与渲染 → 其余）把所有直读写点换掉；
   顺手把逐点热循环换成标量访问器。
3. **真正不建对象数组**：在这一步才让 `points` 留空，并**同时**把不支持的用法做成显式报错。

形态不同的类型（热力图那种「矩阵」）在同一个模板上加一步：**先想清楚它的数据是什么形状**
（点集？矩阵？图？），再决定用哪种列存 —— 热力图的收益（命中 O(1)）其实来自"承认它是矩阵"，
而不是来自"把点换成列"。

纪律一条：**半迁移状态禁止提交**（`points` 已空而仍有站点直读，会造成静默少画 / 提示框空）。

下一步的候选顺序（有需求驱动再做）：

1. 虚拟内容的**导出 / 无障碍**：列转 SVG、按窗口给无障碍节点（引擎侧 P2 也在这条线上）；
2. 分块 + 实时流的组合（滑动窗口跨越块边界时的增量域），以及「分块的热力图」。

已落地：散点、折线、面积（数值列）、热力图（稠密矩阵）、实时流的环形缓冲、亿级数据的分块
按需加载，以及把列交给引擎虚拟子源 —— 2026-09-21 / 22 同批。
